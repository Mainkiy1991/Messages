## ТЕКУЩАЯ РАБОТА: ТЗ №33 «Node 22 → 24» (выдано)
Ветка feat/33-node-24, сложная (CI и деплой), автослияние нет. Меняется: два места node-version в .github/workflows/ci.yml, engines.node в package.json ("24.x"), @types/node (^24, версия не моложе 14 дней, обновление pnpm-lock.yaml только по @types/node), README (RU и EN строки про Node 22). Кода и других зависимостей не трогаем. Тесты числом не меняются (53/152/276/67).
Факты по Render (документация): версия Node выбирается так (по убыванию приоритета): переменная NODE_VERSION в панели, файл .node-version, файл .nvmrc, engines в package.json. В репозитории сейчас только engines "22.x", render.yaml версию не задаёт. Значит после слияния Render возьмёт 24, КРОМЕ случая, если у сервиса в панели задана NODE_VERSION (она сильнее): проверить обоих сервисов (messages-server и messages-web), при необходимости убрать или поставить 24.x, затем Manual Deploy → Clear build cache & deploy.
Проверка версии в CI: pnpm при несовпадении engines лишь предупреждает, CI останется зелёным даже на старой Node: поэтому владелец один раз смотрит в журнале job (Actions → запуск → job checks → шаг setup-node) строку с версией 24.
Откат при проблемах: revert PR (вернуть 22.x и node-version 22), Render соберёт заново.
