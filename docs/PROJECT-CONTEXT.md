## ТЕКУЩАЯ РАБОТА: проект №31 «Общий PIN» (docs/PIN-SYNC-DESIGN.md, черновик 23 ноября)
Суть: сервер хранит один зашифрованный блок «настройки PIN» на аккаунт (по образцу книги контактов: таблица pin_settings, миграция 011, GET/PUT /pin-settings с версией и защитой от перезаписи, ответ 409 version_conflict). Внутри блока (шифрование ключом, выведенным из ключа истории через HKDF, метка messages/v1/pin-settings, паддинг до фиксированной длины): {enabled, pin, updatedAt}. Устройство сверяется с сервером после запуска, разблокировки и входа по сид-фразе: ставит, меняет или убирает свой PIN по версии (в PinState поле syncedVersion; меньшую версию не принимает). Действия пользователя (включить, сменить, выключить, «Сбросить по сид-фразе») требуют связи, при ошибке PIN не меняется и ошибка видна. Конфликт: побеждает первая запись, второе устройство вводит актуальный PIN как доказательство. Не гарантируем: PIN не защищает от владельца сид-фразы (он видит и сбрасывает PIN), другие устройства узнают не мгновенно, откат блока сервером даёт лишь старый PIN на устройстве.
Этапы после утверждения: №31a (сервер + миграция 011 + тесты; владелец применяет миграцию до Merge), №31b (крипто encryptPinSettings/decryptPinSettings + чистая функция решений сверки + юнит-тесты, без интерфейса), №31c (интерфейс, сообщения RU/EN/UK, e2e на двух контекстах, ручная проверка на двух устройствах). Все «сложные», автослияние нет.
ВОПРОСЫ ВЛАДЕЛЬЦУ (ответа ещё нет): 1) как новое устройство получает PIN: A) автоматически (сервер хранит PIN в зашифрованном сид-фразой виде; рекомендация техрука) или B) просит ввести PIN один раз (сервер хранит только проверочный отпечаток); 2) один общий PIN без исключений (рекомендация техрука: да) или разрешить «свой» PIN на отдельном устройстве.
