## ТЕКУЩАЯ РАБОТА: проект №31 «Общий PIN» (docs/PIN-SYNC-DESIGN.md, УТВЕРЖДЁН 23 ноября)
Решения владельца: 1) новое устройство получает PIN автоматически (сервер хранит PIN в зашифрованном ключом истории виде; подсказка «не используйте PIN от банка»); 2) один общий PIN без исключений.
Этапы (все «сложные», автослияние нет): №31a сервер (слит); №31b крипто и ядро клиента (ВЫДАНО, ветка feat/31b-pin-settings-core, ждём отчёт и PR); №31c интерфейс, API-вызовы, тексты RU/EN/UK, e2e на двух контекстах.
Уточнения к проекту, принятые техруком в ТЗ №31b (внести в PIN-SYNC-DESIGN.md после приёмки №31b, с фактическими числами):
1) Версия, которую устройство уже применило, хранится отдельным ключом IndexedDB `pinSyncVersion` (строка, только растёт), а не в PinState: PinState исчезает при выключении PIN, и защита от отката терялась бы.
2) Блок настроек PIN: открытый текст дополняется до фиксированных 512 байт (2 байта длины, JSON, нули), в блоке всегда 553 байта; PIN 6–64 символа (после NFKC); при enabled=false поле pin пустое. Сервер принимает (границы 16–1024 байта), серверный код менять не надо.
3) Решающая функция сверки получает PIN устройства из памяти (при включённом PIN ключи доступны только после его ввода) и возвращает действие: ничего, опубликовать свой, принять версию, включить, сменить, выключить.
Не забыть для №31c: проверить в интерфейсе максимум длины поля PIN (в №31b агент пришлёт grep по maxLength; крипто принимает до 64).
