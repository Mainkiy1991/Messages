## ИДЕЯ
Мессенджер без привязки к почте и телефону. Пользователь создаёт или вводит сид-фразу (12 или 24 слова, BIP-39) и входит с любого устройства: подтягивается история, можно общаться. Всё шифруется и расшифровывается на устройстве, сервер не читает сообщения. Проект открытый, некоммерческий. MVP выполнен (текстовые чаты 1-на-1 в браузере, интерфейс RU/EN/UK), идёт доработка функций и подготовка к аудиту.

## РЕШЕНИЯ ВЛАДЕЛЬЦА (принципы)
- Проект личный и некоммерческий, платит владелец. Платную инфраструктуру (серверы-ретрансляторы и т.п.) пока не берём; вместо неё честные предупреждения пользователю. Позже, при появлении денег, убираем компромисс.

## ПРАВИЛА ПРОЦЕССА (дополнения)
- Из ветки notes PR не создавать и кнопку «Compare & pull request» для неё не нажимать (GitHub показывает её сам после каждой записи в notes): CI проверяет prettier во всех файлах (так появились красные PR #58 и #60). Если PR из notes открылся, просто закрыть.
- Серверное ТЗ не обещает изменений клиента: если клиент не меняется, ожидания UI в e2e не переписывать «под новое поведение».
- Владелец присылает вместе с номером PR и отчёт агента. Код из отчёта сверяю с реальным диффом. Репозиторий публичный: через bash можно клонировать ветку PR и локально прогнать web и crypto тесты (corepack pnpm install --frozen-lockfile, corepack pnpm --filter @messages/web test; pnpm напрямую в песочнице не установлен, нужен corepack); серверные тесты и e2e нужна база, их проверяет CI. Для ветки: git fetch --depth 60 origin main:refs/remotes/origin/main <ветка>:refs/remotes/origin/<ветка>. Для чтения кода main удобно клонировать репозиторий в bash (git clone --depth 1) и искать grep: файлы main.tsx и chat-controller.ts слишком велики для чтения целиком через инструмент.
- Тесты проверять по содержимому, а не по числу: искать тесты, повторяющие SQL сервера внутри самого теста, пустые проверки вида expect(x).toBeTruthy(), мусорные блоки, и сверять названия с обязательными сценариями ТЗ (урок №28b: агент не сообщил, что нет WebSocket-тестов и теста миграции, а часть тестов была пустышками; урок №28c1: агент не добавил 4 обязательных e2e, сославшись на «тяжёлое окружение», хотя CI запускает e2e с сервером, и после замечания добавил; урок №28d: агент не написал обязательные тесты контроллера и поведенческие тесты панели, а один «тест панели» проверяет только статическую разметку загрузки; в отчёте об этом ни слова: всегда сверять список тестов ТЗ с реальным диффом, а не с отчётом; не принимать отговорку, обязательные сценарии выполняются или честно объясняется, почему нельзя). Если агент пишет «CI ещё идёт» или «CI не запускался», смотреть get_check_runs самому. Тестовые строки (User-Agent и т.п.) сверять с настоящими.
