# ПРОЕКТ №28. Активные устройства (сессии)

Черновик техрука, ветка notes. После согласия владельца текст уходит в main как docs/SESSIONS.md в составе ТЗ №28a. Дата: 18 ноября 2026.

## ЦЕЛЬ
Владелец видит список своих устройств, где открыт аккаунт, и может завершить вход на любом из них или на всех, кроме текущего. Типичные случаи: забытый открытый браузер на чужом компьютере, потерянный телефон.

## КАК УСТРОЕНО СЕЙЧАС (по коду)
- Вход без пароля: challenge-response, сервер выдаёт токен на 30 дней и хранит только его хэш в таблице sessions (token_hash, user_id, created_at, expires_at). Метки устройства нет.
- Токен проверяется при каждом HTTP-запросе по базе; WebSocket проверяет его при подключении. Выход (POST /auth/logout) удаляет свою строку и закрывает свои сокеты (closeWebSocketsForToken).
- Каждый вход создаёт новую строку sessions; одно устройство со временем оставляет несколько строк.

## ГЛАВНАЯ ПРОБЛЕМА
Если просто удалить строку сессии другого устройства, оно тут же войдёт заново: на ответ 401 клиент молча вызывает connection.refreshSession() (loginToServer), а ключи у него лежат в IndexedDB. WebSocket с кодом 4401 тоже запускает немедленный повторный вход. То есть удаление токена ничего не отзывает. Аккаунт = публичный ключ из сид-фразы, у него нет «пароля, который можно сменить» и ключ нельзя ротировать.

## РЕШЕНИЕ
Устройству даём случайный идентификатор, сервер запоминает «отозванные» и отказывает им во входе; честный клиент, получив такой отказ, стирает у себя сессию и просит сид-фразу.

1. deviceId: 16 случайных байт (32 hex), клиент создаёт при первом входе в этом браузере и хранит в IndexedDB рядом с сессией. Не секрет. При «Выйти» или принудительном выходе удаляется; новый вход по сид-фразе создаёт новый deviceId.
2. Метка устройства: клиент составляет {браузер, ОС} крупно (Chrome / Firefox / Safari / Edge; Windows / macOS / Linux / Android / iOS; иначе «неизвестно»), шифрует ключом истории (как книга контактов) и отправляет при входе. Сервер метку не видит. Язык подписей подставляет клиент при показе.
3. Миграция 010 (только добавляющая, совместима со старым кодом):
   - таблица devices(user_id, device_id, label_ciphertext, created_at, last_seen_at, revoked_at null), PRIMARY KEY(user_id, device_id), user_id ссылается на users с ON DELETE CASCADE;
   - sessions.device_id text null; индекс (user_id, device_id).
4. POST /auth/login: новые необязательные поля deviceId (32 hex) и deviceLabel (строка до 512 символов). Без них вход как раньше (старая сессия без устройства). С ними: после проверки подписи, если устройство отозвано (revoked_at не null) → 403 {error:"device_revoked"} (подпись проверена, поэтому узнаёт только владелец ключа); иначе upsert устройства (метка, last_seen_at) и сессия с device_id. Лимит 20 неотозванных устройств на аккаунт: при 21-м вытесняется давнее по last_seen_at (его сессии удаляются, сокеты закрываются). Отозванных запоминаем до 100 (старые удаляются).
5. GET /devices (авторизован): {devices:[{deviceId, labelCiphertext, createdAt, lastSeenAt, current}]} только неотозванные, current = устройство токена вызывающего.
6. DELETE /devices/:deviceId → 204: ставит revoked_at, удаляет все сессии устройства, закрывает их сокеты (код 4401 уже обрабатывается клиентом); повтор → 204; нет такого → 404; своё текущее → 409 {error:"current_device"} (для него есть «Выйти»).
7. POST /devices/revoke-others с телом {} → {revoked:n}: то же для всех, кроме текущего.
8. last_seen_at обновляется при входе, при WS-аутентификации и при закрытии сокета. IP и user-agent сервер не хранит и не логирует.
9. Лимиты запросов: GET /devices 60/мин, DELETE и revoke-others 20/мин.
10. Клиент: если loginToServer получил 403 device_revoked, то (в одном месте, connection.refreshSession) локально стираются сессия, PIN-блоб, ключи, очередь, deviceId (как «Выйти», без вопроса про сид), показывается экран входа с видимым сообщением «Этот вход завершён на другом устройстве. Войдите снова по сид-фразе». Под PIN-блокировкой это произойдёт при разблокировке (токена в памяти нет), данные на диске до того защищены PIN.
11. Интерфейс: в профиле раздел «Устройства»: строки (метка, «это устройство», последняя активность), кнопка «Завершить» с подтверждением на самой кнопке, кнопка «Завершить на всех остальных». Ошибки видны в интерфейсе. Тексты на RU, EN, UK.

## ЗАЩИТА
- Сервер не получает ни сид-фразы, ни ключей; метка шифруется ключом истории, deviceId случаен и не связан с аппаратурой.
- Отзыв требует действующей сессии; чужой отозвать нельзя (запросы привязаны к user_id токена).
- Эффект сразу для HTTP (токены удалены), для сокетов (закрываются), для повторного входа (403).

## ЧЕГО НЕ ГАРАНТИРУЕМ (честно показать в интерфейсе и документации)
- Не защищает от человека, у которого есть сид-фраза или скопированные ключи: он войдёт как новое устройство. Ключ аккаунта нельзя сменить (адрес = ключ). От украденных ключей спасает только PIN и осторожность.
- Защищает от «забытого открытого браузера» и от честного клиента (наш сайт без модификаций).
- Выключенное или офлайн-устройство узнает об отзыве только при следующем обращении к серверу; до тех пор данные в нём остаются (под PIN зашифрованы).
- Изменённый клиент может проигнорировать отзыв (как и удаление сообщений).
- Отзыв не стирает то, что устройство уже скачало и расшифровало.
- Сервер видит метаданные: сколько устройств, когда входили (метки не видит).
