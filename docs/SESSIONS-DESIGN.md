# ПРОЕКТ №28. Активные устройства (ключи устройств)

Версия 2, утверждена владельцем 19 ноября 2026 (усиленный вариант). Ветка notes. Текст уходит в main как docs/SESSIONS.md в составе ТЗ №28b.

## ЦЕЛЬ
Владелец видит список своих устройств и завершает вход на любом из них или на всех, кроме текущего. После «Завершить» устройство не получает доступа, даже если на нём изменённый сайт или скопированы все данные браузера.

## КАК УСТРОЕНО СЕЙЧАС (по коду)
- Аккаунт = ключ личности Ed25519 из сид-фразы. Вход: challenge-response, ключ личности подписывает случайную строку (signAuth). Сервер выдаёт токен на 30 дней, хранит его хэш в sessions.
- Браузер хранит в IndexedDB (messages-session): ключ личности, ключ шифрования, ключ истории, токен, состояние PIN; в messages-outbox зашифрованную очередь неотправленных. Историю и чаты не хранит: всё грузится с сервера при каждом открытии. Куки не используются.
- Ключ личности нужен только для входа на сервер (signAuth, signKeyBinding при входе) и как основа ключа, защищающего токен при PIN (wrapServerSession). Сообщения им не подписываются.

## ГЛАВНАЯ ПРОБЛЕМА
Если удалить токен другого устройства, оно молча входит заново: ключ личности лежит в браузере, клиент на 401 вызывает refreshSession(), а WebSocket с кодом 4401 запускает немедленный вход. Одноразовый ключ на сессию тоже не помогает: тот, кто скопировал браузер, копирует и его. Отзыв держится только если на устройстве нет секрета, которым можно выписать себе новый доступ.

## РЕШЕНИЕ: КЛЮЧ УСТРОЙСТВА, КЛЮЧ ЛИЧНОСТИ НА УСТРОЙСТВЕ НЕ ХРАНИТСЯ
1. Ключ устройства: случайный Ed25519, создаётся при входе по сид-фразе. deviceId = публичный ключ устройства в hex (64 символа).
2. Регистрация (вход по сид-фразе): клиент запрашивает challenge, ключ личности подписывает сообщение `messages/v1/device-register\n<challengeId>\n<challenge>\n<deviceId>` (в подписанное входит публичный ключ устройства), отправляет вместе с ключом шифрования, подписью привязки ключа и зашифрованной меткой. Сервер проверяет, создаёт устройство и сессию. После этого ключ личности стирается из памяти и никогда не пишется в IndexedDB.
3. Вход устройства: challenge подписывается ключом устройства (`messages/v1/device-auth\n<challengeId>\n<challenge>`). Сервер находит устройство по deviceId, проверяет подпись, и только после этого сообщает об отзыве (403 device_revoked), чтобы статус не узнавал тот, у кого нет ключа устройства. Иначе выдаёт токен.
4. Отзыв: сервер ставит revoked_at, удаляет сессии устройства, закрывает его сокеты. Отозванное устройство не может войти, а выписать новое разрешение без ключа личности нельзя (он есть только у сид-фразы).
5. На устройстве хранятся: ключ устройства, ключ шифрования, ключ истории (они нужны для чтения), токен, состояние PIN, публичный ключ личности (публичный). Токен при PIN защищается ключом, производным от ключа устройства (раньше от ключа личности).
6. Метка устройства {браузер, ОС} (крупно: Chrome/Firefox/Safari/Edge, Windows/macOS/Linux/Android/iOS, иначе «unknown») шифруется ключом истории (XChaCha20-Poly1305, AAD = deviceId), сервер её не видит.
7. Старые клиенты (ключ личности в браузере) продолжают работать через прежний POST /auth/login до этапа №28c. Вошедший браузер при первом открытии новой версии молча регистрирует ключ устройства (подписав ключом личности, пока он ещё есть) и стирает ключ личности.

## СЕРВЕР (миграция 010, только добавляющая)
- devices(device_id text PRIMARY KEY (64 hex), user_id text NOT NULL REFERENCES users ON DELETE CASCADE, label_ciphertext text NOT NULL, created_at, last_seen_at, revoked_at null); индекс по (user_id).
- sessions.device_id text null (для старых входов null); индекс (device_id).
- POST /auth/device/register, POST /auth/device/login (обе с лимитом 20/мин, используют /auth/challenge); GET /devices; DELETE /devices/:deviceId (204, повтор 204, нет 404, свой текущий 409 current_device); POST /devices/revoke-others с телом {} → {revoked:n}.
- last_seen_at обновляется при регистрации, входе устройства, WS-аутентификации и закрытии сокета. IP и user-agent не хранятся.
- Лимиты: до 20 неотозванных устройств на аккаунт (при 21-м вытесняется давнее по last_seen_at), отозванные помнятся до 100.

## КЛИЕНТ ПРИ ОТЗЫВЕ
loginToServer получает 403 device_revoked в одном месте (connection.refreshSession): стираются токен, ключи, PIN-блоб, очередь, ключ устройства; экран входа с видимым сообщением «Этот вход завершён на другом устройстве. Войдите снова по сид-фразе». При PIN-блокировке это произойдёт при разблокировке (токена в памяти нет); данные на диске до тех пор зашифрованы.

## ЧТО НЕ МЕНЯЕТСЯ
Сид-фраза и деривация ключей, формат сообщений v2, шифрование, история, книга контактов, идея PIN. Новых самописных алгоритмов нет: подписи Ed25519, HKDF и XChaCha20-Poly1305 из @noble, как в проекте.

## ЧЕГО НЕ ГАРАНТИРУЕМ (показать честно в интерфейсе и документации)
- Против человека, у которого есть сид-фраза: он регистрирует своё устройство. Ключ аккаунта сменить нельзя (адрес = ключ).
- Против того, кто скопировал ключ личности из браузера старой версии до перехода на ключи устройств: этот ключ остаётся действующим навсегда. Для нового проекта владелец принимает риск (браузеры переводятся сразу после выпуска №28c).
- Тот, кто скопировал данные браузера и ключ устройства ДО отзыва, до отзыва имеет доступ и мог скачать историю; скопированные ключи шифрования расшифруют то, что уже скачано (нет forward secrecy).
- Выключенное или офлайн-устройство узнает об отзыве при следующем обращении к серверу.
- Отзыв не стирает то, что устройство уже расшифровало.
- Сервер видит метаданные: сколько устройств и когда входили; метку устройства не видит.

## ЭТАПЫ
- №28a, сложная, автослияние нет: packages/crypto (generateDeviceKeys, deviceIdFromPublicKey, signDeviceRegistration/verifyDeviceRegistration, signDeviceAuth/verifyDeviceAuth, encryptDeviceLabel/decryptDeviceLabel), тесты, абзац в docs/CRYPTO.md.
- №28b, сложная, миграция 010 (владелец применяет к боевой базе до Merge): сервер (все эндпоинты выше), docs/SESSIONS.md, серверные тесты. Старый /auth/login остаётся.
- №28c, сложная: клиент (ключ устройства, регистрация при входе, вход ключом устройства, стирание ключа личности, перенос уже вошедших браузеров, токен под PIN от ключа устройства, обработка device_revoked, тесты web и e2e). Если не уложится в лимит, две части в одной ветке. После слияния владелец обновляет страницу на всех своих устройствах.
- №28d, простая: список устройств в профиле, «Завершить» с подтверждением на кнопке, «Завершить на всех остальных», тексты RU/EN/UK, e2e.
- №28e, сложная (малая): сервер отключает старый POST /auth/login (вход только через register/device login). Без этого этапа защита неполная: ключ личности, скопированный со старого браузера, продолжает входить без устройства.

## ПОКА НЕ ДЕЛАЕМ
Уведомление «вошли с нового устройства», подтверждение нового входа со старого устройства, вход по QR, показ IP и города, ротация ключа личности (невозможна: адрес = ключ).
