## ИДЕЯ
Мессенджер без привязки к почте и телефону. Пользователь создаёт или вводит сид-фразу (12 или 24 слова, BIP-39) и входит с любого устройства: подтягивается история, можно общаться. Всё шифруется и расшифровывается на устройстве, сервер не читает сообщения. Проект открытый, некоммерческий. MVP выполнен (текстовые чаты 1-на-1 в браузере, интерфейс RU/EN/UK), идёт доработка функций и подготовка к аудиту. Сейчас проектом пользуются владелец и 1–2 тестера.

## ПРИНЦИПЫ И РЕШЕНИЯ ВЛАДЕЛЬЦА
- Проект личный и некоммерческий, платит владелец. Платную инфраструктуру (серверы-ретрансляторы и т.п.) пока не берём; вместо неё честные предупреждения пользователю. Позже, при появлении денег, убираем компромисс.
- Максимально близко к концепции: без привязки к почте и телефону, всё зашифровано. Экономим токены агента: ТЗ маленькие.
- Не перестраховываться ради пользователей, которых нет (22 ноября владелец остановил ТЗ №28e1): совместимость со старыми версиями и экраны миграции делаем только когда появятся реальные чужие пользователи (перед публикацией); сейчас достаточно написать тестерам «выйди и войди заново». Перед каждым ТЗ про совместимость спрашивать себя: у кого это реально сломается?
- Полный аудит безопасности откладывается до момента, когда все желаемые функции сделаны и решено публиковать проект. До аудита адрес сайта не публикуем и чужих людей не зовём. Каждое «сложное» ТЗ проверяется построчно.
- Очистка чата оставляет контакт в списке (чтобы не потерять ID собеседника); удаление чата убирает его из списка. Старые очищенные и удалённые чаты (до миграции 009) остаются скрытыми.
- Интерфейс: подтверждение копирования показывается на самой кнопке; корзинка в списке на компьютере появляется через ~1 с после наведения и не остаётся на выбранном чате.
- Сроки не срочных пожеланий («Контакты» и др.) техрук определяет сам.
- Контекст ведётся, чтобы вести проект к цели, а не чтобы укладываться в лимит. Из файлов ничего нужного не удаляется, сворачивается только выполненное (старые версии остаются в истории коммитов ветки notes). ## ПРАВИЛА ПРОЦЕССА (дополнения к инструкциям проекта)
- Из ветки notes PR не создавать и кнопку «Compare & pull request» для неё не нажимать (GitHub показывает её сам после каждой записи в notes): CI проверяет prettier во всех файлах (так появились красные PR #58 и #60). Если PR из notes открылся, просто закрыть.
- Серверное ТЗ не обещает изменений клиента: если клиент не меняется, ожидания UI в e2e не переписывать «под новое поведение».
- Владелец присылает вместе с номером PR и отчёт агента. Код из отчёта сверяю с реальным диффом. Репозиторий публичный: через bash можно клонировать ветку PR и локально прогнать web и crypto тесты (corepack pnpm install --frozen-lockfile, corepack pnpm --filter @messages/web test; pnpm напрямую в песочнице не установлен, нужен corepack); серверные тесты и e2e нужна база, их проверяет CI. Для ветки: git fetch --depth 60 origin main <ветка>:refs/remotes/origin/<ветка>. Для чтения кода main удобно клонировать репозиторий в bash (git clone --depth 1) и искать grep: файлы main.tsx и chat-controller.ts слишком велики для чтения целиком через инструмент.
- Тесты проверять по содержимому, а не по числу: искать тесты, повторяющие SQL сервера внутри самого теста, пустые проверки вида expect(x).toBeTruthy(), мусорные блоки, дубли, и сверять названия с обязательными сценариями ТЗ (урок №28b: агент не сообщил, что нет WebSocket-тестов и теста миграции, а часть тестов была пустышками; урок №28c1: агент не добавил 4 обязательных e2e, сославшись на «тяжёлое окружение», хотя CI запускает e2e с сервером; урок №28d: агент не написал обязательные тесты контроллера и поведенческие тесты панели, а один «тест панели» проверяет только статическую разметку; в отчёте об этом ни слова: всегда сверять список тестов ТЗ с реальным диффом, а не с отчётом; не принимать отговорку, обязательные сценарии выполняются или честно объясняется, почему нельзя). Если агент пишет «CI ещё идёт» или «CI не запускался», смотреть get_check_runs самому. Тестовые строки (User-Agent и т.п.) сверять с настоящими. Ослабление старых тестов искать так: git diff origin/main HEAD -- тесты | grep '^-.*expect'. Тест «повторов нет» обязан промотать время вперёд, иначе он ничего не доказывает; такие тесты проверять мутацией (временно убрать защиту, тест должен упасть; для web делается в клоне через sed/python, затем cp из резервной копии). В проекте нет jsdom и testing-library: тесты компонентов только по статической разметке, интерактив проверяет e2e (или логику выносить в чистые функции). Если удалённый тест защиты заменяется другим, требовать поимённую таблицу «удалённый тест → эквивалент» (так принят №28e).
- В e2e не добавлять фиксированные ожидания и sleep без согласования с техруком (урок №28d: агент 7 раз чинил e2e вслепую, так как локально e2e не запускается, и в итоге добавил 61-секундное ожидание в afterAll). Лимит 20 запросов в минуту на /auth/challenge общий для всех спецификаций (один IP, workers 1): в ТЗ с e2e ограничивать число входов по сид-фразе и просить сначала прочесть образец (device.spec.ts, devices.spec.ts).
- Урок №28d (ручная проверка): CI-e2e идёт на сервере без прокси, поэтому не доказывает, что поведение через боевой хост (Render) такое же; всё, что зависит от WebSocket и кодов закрытия, сверяется ручной проверкой на сайте, и протокол не должен зависеть от кода закрытия (нужны обычные кадры данных). При расхождении CI и боевого сайта не гадать: сначала диагностика (DevTools владельца: Network, фильтр WS и запросы, панель Messages), потом ТЗ.
- Урок №28d2: агент не запустил свои тесты под Node 22 (CloseEvent там нет) и CI покраснел. В ТЗ с WebSocket-тестами напоминать: в Node 22 нет глобальных CloseEvent и т.п., использовать Event с полем code. Агенты дублируют тесты, чтобы набрать «+4»: смотреть, что новые тесты различаются по сценарию.
- Урок №28e1: перед ТЗ на совместимость или миграцию сверяться с принципом «не перестраховываться» и предлагать самый дешёвый вариант (сообщение людям вместо кода).
- Серверные тесты агенты локально не запускают (нет PostgreSQL), поэтому большие правки серверных тестов (например, общий помощник на 172 вызова) идут двумя частями с PR после первой (CI проверяет), красный CI чинится в той же ветке по ошибке из лога, которую копирует владелец (так прошёл №28e: часть A, PR, часть B, один красный CI не потребовался).
- Размер файлов контекста: PROJECT-CONTEXT.md (живой) ориентир до ~8 КБ и переписывается при каждом вердикте; PROJECT-BASE.md (этот) до ~45 КБ и правится редко; TECH-DECISIONS.md до ~40 КБ, правится только когда этап меняет устройство системы. Сворачивать только то, что реально устарело; полезное не выбрасывать.
- В CSS не использовать :focus-within для показа скрытых кнопок (клик мышью даёт фокус); использовать :focus-visible. В e2e для клавиатурного фокуса идти клавишей Tab при мыши вне строки (не .focus() и не при наведении).
- Номера: доработки к принятому ТЗ получают суффикс (№29a); №28 это «Активные устройства» (этапы №28a, №28b, №28c1 вместе с №28c1a и №28c1b, №28d, №28d1, №28d2, №28e; №28c2 и №28e1 отменены). Доработка открытого PR идёт в том же чате агента и той же ветке (не новое ТЗ).
- Геометрические критерии в ТЗ (доля ширины, позиции) сверять с данными конкретного теста: у короткого сообщения пузырь по ширине текста, требовать от него долю ширины нельзя (урок №30). В каждом ТЗ с CSS агенту писать: «если требование ТЗ нельзя выполнить без правил вне ТЗ, не подгоняй CSS, остановись и сообщи в отчёте». В диффе CSS проверять, что нет правил вне ТЗ (особенно width/flex).
- Для накладок и позиционирования считать цифры на бумаге до ТЗ: высота кнопки, смещение, внутренний отступ пузыря, отступ списка (урок №30). Смотреть скриншот владельца на телефоне, а не только тесты.
- Если владелец пишет, что PR создать нельзя («nothing to compare»): агент запушил ветку до коммита. Лечится коммитом и пушем в ту же ветку. Перед советами проверять через list_branches и list_commits, не влит ли уже PR (ветки после слияния удаляются сами). В каждое ТЗ писать: «перед пушем git status чистый, коммит с изменениями есть в git log».
- Миграции: порядок для владельца в PR с миграцией (PowerShell): git fetch origin, git checkout <ветка PR>, git pull, $env:DATABASE_URL = Read-Host "строка подключения" (строку в чат не пересылать), pnpm --filter @messages/server migrate, Clear-Host, $env:DATABASE_URL = $null, git checkout main; только потом Merge.
